# M5-03 效能優化：第一批量測與修正

本卡尚未全部完成。已實作可重跑的量測、去除重複運算並完成回歸；10 萬人口完整 tick 尤其每日結算仍超過 TECH §10 的 30 ms，不能勾選「所有預算達標」。

## 範圍與方法

2026-10-11，同一台 macOS arm64／Apple M4／Node v24.19.0。基準為 `cbe0cb0288696dab2f52c991e9d145cdb61614d3`，先加入同一測量 fixture，執行修改前量測；之後再改正式程式。原始數據放在 `performance/m5-03/`，沒有把不同硬體或不同人口的結果混在一起。

CPU fixture 是人工建立的 1,000 棟住宅、1,000 棟工業、32 棟商業、32 條道路與真正的 100,000 位居民；不是自然成長、供應完整的城市，也不是 M5-04 壓力存檔。購物測量為 13:00 重複相同請求突發，12 輪扣除前兩輪；完整模擬為 05:00 起 60 個連續 tick，包含 6 次每日結算，末尾人口兩版均為 99,066。完整 tick 不排除首次快取建立與結算尖峰。Node sink 是空函式，不包含瀏覽器 postMessage／GPU 成本，因此數據也不能當作 Worker 的最壞上限。

購物排程平均減少約 96.5%，完整 tick 平均減少約 21.8%；沒有降低居民數量、略過結算、修改模擬速度或放寬 30 ms 目標。單次取樣有機器排程／GC 誤差，不是跨設備保證。

- 同一 tick 先收集可用商店／公園，按起點共用最近目的地查詢；個人機率、班表、目的地 ID、交通請求與抵達確認維持不變。每 tick 清除快取，建築變成荒廢、斷路、刪除立即生效；零結果也快取，等距仍選較小 ID。
- 電網只保留形狀相同時的連線圖；逐點比較並保留座標副本，所以原地移動電線、旋轉建築、改尺寸／順序也會重建。每次重算發電、用電、政策、服務旗標與優先順序。
- 健康政策由逐人查詢改成單次更新按住宅查詢，仍逐人更新與彙總健康。
- 主幀讀取相機距離不再製作狀態快照；建築更新使用 Map.values，避免每棟每幀產生解構配對陣列。

## 診斷契約

`?debug=1` 顯示 FPS、繪製數、三角形、render callback P95、Worker tick P95 及主頁 JS heap。兩側採固定 240 筆 ring，每次記錄不配置新物件；統計時才排序／產生摘要。Worker 只在 debug 命名啟用逐 tick 計時，每秒傳送一次 performance event，沒有每 tick 新增 IPC。純讀取指標不改世界，非 debug 遊戲不進行 tick 計時。paused 不加入零值稀釋耗時。不可用 callback 耗時替代 GPU 或整個主執行緒忙碌時間。

記憶體 API 不可用時顯示「無資料」。量測介面不觸發自動降畫質／存檔；那些壓力處理屬 M5-04。除錯面板高度由 ResizeObserver 提供，手機橫式避開左側工具列。
