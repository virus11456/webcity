# M5-03 效能優化：量測與修正

本卡尚未全部完成。已實作可重跑的量測、去除重複運算並完成回歸；10 萬人口完整 tick 尤其每日結算仍超過 TECH §10 的 30 ms，不能勾選「所有預算達標」。

## 範圍與方法

2026-10-11，同一台 macOS arm64／Apple M4／Node v24.19.0。基準為 `cbe0cb0288696dab2f52c991e9d145cdb61614d3`，先加入同一測量 fixture，執行修改前量測；之後再改正式程式。原始數據放在 `performance/m5-03/`，沒有把不同硬體或不同人口的結果混在一起。

CPU fixture 是人工建立的 1,000 棟住宅、1,000 棟工業、32 棟商業、32 條道路與真正的 100,000 位居民；不是自然成長、供應完整的城市，也不是 M5-04 壓力存檔。購物測量為 13:00 重複相同請求突發，12 輪扣除前兩輪；完整模擬為 05:00 起 60 個連續 tick，包含 6 次每日結算，末尾人口兩版均為 99,066。完整 tick 不排除首次快取建立與結算尖峰。Node sink 是空函式，不包含瀏覽器 postMessage／GPU 成本，因此數據也不能當作 Worker 的最壞上限。

- 同一 tick 先收集可用商店／公園，按起點共用最近目的地查詢；個人機率、班表、目的地 ID、交通請求與抵達確認維持不變。每 tick 清除快取，建築變成荒廢、斷路、刪除立即生效；零結果也快取，等距仍選較小 ID。

- 健康政策由逐人查詢改成單次更新按住宅查詢，仍逐人更新與彙總健康。

## 診斷契約

`?debug=1` 顯示 FPS、繪製數、三角形、render callback P95、Worker tick P95 及主頁 JS heap。兩側採固定 240 筆 ring，每次記錄不配置新物件；統計時才排序／產生摘要。Worker 只在 debug 命名啟用逐 tick 計時，每秒傳送一次 performance event，沒有每 tick 新增 IPC。純讀取指標不改世界，非 debug 遊戲不進行 tick 計時。paused 不加入零值稀釋耗時。不可用 callback 耗時替代 GPU 或整個主執行緒忙碌時間。

記憶體 API 不可用時顯示「無資料」。量測介面不觸發自動降畫質／存檔；那些壓力處理屬 M5-04。除錯面板高度由 ResizeObserver 提供，手機橫式避開左側工具列。

每日結算平均減少約 11.1%，最大 tick 耗時的中位數減少約 27.0%；每 tick 30 ms 仍未達標。所有輪次起始／結束人口均為 100,000／99,066。Node 空 sink 不涵蓋 Worker IPC 或 GPU；此次沒有 UI 變更，沒有重跑或更新第一批瀏覽器數據。

本批調整：

- 電網重建先比較形狀包圍盒的最短距離，排除同一空間桶內確定超出傳電距離的候選；可能連接者仍跑原本精細足跡／線段距離。電網群組、供需和缺電旗標維持原規則，沒有因缺少電廠略過結算。
- 保留既有工作與建立待業名單共用一次居民遍歷，所有舊職位仍先保留，之後才依原本順序招募。住家就業彙總使用精確整數鍵代替每人建立字串，支援 Int32 工作地點 ID 與四種學歷。
- 人口變更偵測在單次更新前複製數值、更新後比較，涵蓋家庭組成、年齡／學歷彙總、職位分配、遷移日期與待處理遺體；避免兩次 JSON 序列化，不依賴可被原地修改的物件參照。
- 健康逐人迴圈一次取得住宅的恢復值、政策倍率與彙總物件；個人小數健康及每日防重複結算維持原規則。
- 地價平滑的內部格直接讀取九個鄰格，維持原本相加順序；邊界格維持原本規則。環境摘要改為逐欄位比較，省去 JSON 字串。

驗證：新增人口 patch 與 JSON 參考結果比對、最大正 Int32 相鄰工作地點 ID、不同住家健康小數、1／2／3／17／300 格平滑與邊界參考演算法、旋轉建築／開放電線和全配對電網連線比對。另以兩個版本各跑 60 tick，每 tick 呼叫 snapshot 後對完整 JSON 計算 SHA-256，60 筆全部一致；原始雜湊與方法見 [daily-replay.json](performance/m5-03/daily-replay.json)。這是該固定場景的等價證據，不代表所有可能城市均已驗證。

- ServiceNetwork 接入查詢先以道路／取樣線段的包圍盒排除不可能接入者，候選仍做精確最近點計算，保留最近道路、等距順序、高架／高速公路排除以及建築退縮距離。包圍盒與既有道路取樣一起重建，不快取居民或服務供需。

驗證包含曲線／等距道路、接入容差邊界、不同退縮量的全線段參考比對；逐居民計數的學校需求參考比對；同一住家不同學歷、保留原校、滿額候補、預算縮減、停用及斷路的個人入學結果。提交檢查：1,098 項單元測試、lint、typecheck、production build 通過。本批純模擬／查詢優化，未改 UI，也沒有重跑瀏覽器 E2E。`npm run perf:sim` 現在同時執行無學校與 96 校兩種量測；新測試不把耗時數值當作達標門檻。

## 第五批：垃圾與殯葬派車查詢（2026-10-12）

以 `16d8b028f36a27e30513b63fcc50384c5fe742ad` 為基準。CPU 取樣發現，GarbageSystem／DeathcareSystem 在每個待收運目標上掃描所有建築；沒有可出勤設施時不消耗尋路次數，仍會對全部目標重複掃描。這是一般 tick 和換日 tick 都會支付的成本。

本批每 tick 在處理抵達／重試後建立設施候選清單，以及按設施彙總的在途車數、已預留貨量。預留包含 collect 與 return 兩階段，派車成功後立即增加；下一個 tick 重算，拆除、到站卸載、火災、停用及預算變動仍依既有狀態生效。每個目標仍重新篩選容量並按距離／ID 排序，保留輪巡 cursor、失敗尋路消耗的預算、任務上限與實際往返路線。沒有設施時也保留目標輪巡，不提前 return 改變日後服務順序。

同一 Apple M4／Node v24.19.0，修改前後交替各三個獨立程序。使用第四批的 10 萬人口、96 校、60 tick／6 次換日場景；新增獨立派車場景：同一道路沿線放置 2,000 個收運目標、32 座垃圾設施與 32 座墓園，執行 40 tick，真實 traffic.step 在派車計時區間外，保留所有冷啟動樣本。這是人工工作負載，不代表完整自然城市。完整原始資料見 [dispatch-cpu-repeats.json](performance/m5-03/dispatch-cpu-repeats.json)。

10 萬人口場景沒有垃圾／殯葬設施，所以收益主要來自避免反覆掃描無法供應服務的建築；完整 tick 平均下降約 39.8%，換日平均下降約 15.3%。64 座設施場景的收益較小，不把兩種數字混用，也不將平均低於 30 ms 解讀為每 tick 達標。P95 與換日仍超標，M5-03 保持未完成；瀏覽器 IPC／GPU、真機記憶體不在本次量測內。

三輪前後，10 萬人口場景的服務更新與 60 tick 後完整狀態雜湊各自一致，結束人口均為 99,066。實際派車場景結束均保留 29 個垃圾任務、33 個殯葬任務，包含 traffic.snapshot 的完整狀態 SHA-256 六次完全一致。新增六項測試涵蓋無設施時的輪巡、新增設施、同距離 ID 優先、逐筆容量預留、在途回程占位與拆除重建；既有實際收運／卸載、斷路恢復及存讀檔測試繼續驗證。
